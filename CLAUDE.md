# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Flaney Associates is a static marketing website for a materials engineering consultancy. It is deployed via GitHub Pages at **https://jotaigbe2026.github.io/Flaney_Associates**.

There is no build system, bundler, or package manager. The site is pure HTML/CSS/JS.

The site has three parts:
- `index.html` — the single-page marketing site.
- `blog/` — the blog archive imported from the live WordPress site at flaneyassociates.com. Generated by a script; see **Blog** below.
- `publisher/` — an authoring dashboard for writing the monthly post. See **Publishing a monthly post** below.

## Running Locally

```bash
python3 -m http.server 8000
# then open http://localhost:8000
# the authoring dashboard is at http://localhost:8000/publisher/
```

This is required (rather than opening index.html directly) because the gated PDF download system and the publisher both use `fetch()`, which is blocked by browsers on `file://` URLs.

## Publishing a monthly post

`publisher/` is a static dashboard for composing one post a month. Nothing about it is privileged — it is the same HTML/CSS/JS as the rest of the site, and it runs entirely in the browser. It cannot write to the repository, so it hands back every file a publish touches and you commit them.

1. Open `http://localhost:8000/publisher/`.
2. **Start next month's post** fills in the date, author and categories from the monthly template. The date is the first month not already taken by a post, so several months can be queued in one sitting.
3. Paste the article, pick categories, drop in a featured image.
4. **Generate the publish bundle** produces six files, downloadable individually or as one zip:

| File | |
|---|---|
| `blog/<slug>.html` | the new article page |
| `blog/images/<slug>.<ext>` | the featured image |
| `articles/<slug>.pdf` | the gated download |
| `blog/data/posts.json` | replaced, with the new post merged in |
| `blog/index.html` | replaced — the archive, regenerated |
| `index.html` | replaced — the homepage "latest posts" strip |

5. Unzip over the repository root and commit. Running `python3 generate_blog.py` afterwards is optional and produces no diff.

### Editing a published post
The **Edit published** tab in step 2 lists the 19 posts whose body actually lives on this site (gated posts are excluded — their text has never been here, so an edit would look like it silently failed). Choosing one loads it back into the form; **Generate** then rebuilds the same files with `replace` status rather than creating new ones.

Three deliberate constraints:

- **The slug is locked.** Changing a live URL breaks every LinkedIn post and search result pointing at it, and strands the old page — the bundle has no way to delete a file.
- **The date is locked.** A correction is not a republication, so a typo fix does not get promoted to the top of the archive and the homepage.
- **The PDF is rebuilt** from the edited text, so a reader can never download a PDF contradicting the corrected page.

Two things make this work, and both are easy to break:

**The body is loaded from the rendered page, not from `posts.json`.** `posts.json` holds the *raw* WordPress markup — shortcodes, editor attributes, the lot — and `clean()` is applied by `generate_blog.py` at render time. Loading that raw source would show markup the author never wrote. `loadBody()` therefore fetches `blog/<slug>.html` and takes `.article-body`'s innerHTML, which is the authoritative cleaned text.

**`build_post()` skips `clean()` for `local`/`edited` posts.** `clean()` is *not* idempotent: `promote_pseudo_headings()` promotes bold runs the previous pass left alone, so a second pass keeps changing the text (measured: only 5 of 19 rendered bodies survive a second `clean()` unchanged). Since the publisher stores already-clean content, re-cleaning would rewrite the article on every regeneration. Both renderers now use an edited body verbatim, which is what makes their output byte-identical — verified by SHA-256 on a real edit.

A consequence worth knowing: `template.js`'s `article()` renders `content` verbatim and so is only correct for `local`/`edited` posts. That is all it is ever asked to do — the bundle writes exactly one article page, the post being created or edited — but do not reuse it to render an imported post.

### Getting a bundle into the repo
The Files tab prints one command that unzips the bundle, commits and pushes. **Double-clicking the zip in Finder does not work** — macOS extracts it into a new folder rather than merging it into the repo, so the files land in the wrong place. `unzip -o` merges and overwrites without prompting.

The command picks the newest matching download (`ls -t | head -1`) because a second download of the same post arrives as `flaney-<slug>-1.zip`, and unzipping the older one would quietly publish a stale bundle.

The repository path it needs lives in `localStorage` under `flaney_publisher_paths`, **not** in `template.json` — that file is committed and served publicly, and a local filesystem path (with the machine's username in it) does not belong there. The field is in step 1; without it the command shows a placeholder.

### The monthly template
Defaults live in **`publisher/template.json`**, committed to the repo:

| Field | Current setting | |
|---|---|---|
| `titlePattern` | `""` (empty) | Deliberate — a fresh headline is written each month. Every one of the 55 archived titles is an editorial headline, and dated ones perform worse when shared. A non-empty pattern supports `{month}`, `{year}`, `{month_short}`, `{n}`. |
| `author` | `Joshua Otaigbe` | The July 2026 post moved to a named byline; the rest of the archive is `Editorial Team`. |
| `publishDay` | `15` | The 14th and 15th account for 12 of 55 posts — more than any other date. |
| `categories` | `Advanced Materials Engineering` | The most-used category, on 35 of 55 posts. |
| `byline` | name + role credential | Signed at the end of every post, above the PDF box. Wrapped in `<p><em>…</em></p>` — **an inline tag, never a class**, because `clean()` strips `class` attributes and any styling done that way would vanish on the first regeneration. `<em>` survives `clean()` intact and round-trips unchanged. `toBlocks()` carries the italics into the PDF too. The older key name `closing` is still read as a fallback so a per-device override saved before the rename still loads. |

`localStorage` (`flaney_publisher_template`) holds a **per-device override** that wins over the file; the status line in the panel header says which is in effect. *Save for this browser* writes the override, *Download for repo* writes `template.json` back out so a change can be committed and picked up everywhere. The file is optional — the dashboard falls back to `localStorage` alone if it is missing.

An empty `titlePattern` is treated as a setting, not as missing data: **Start next month's post** fills in everything else and puts the cursor in the title field.

### publisher/ is served publicly
Pages serves the whole repository, so the dashboard is live at `/Flaney_Associates/publisher/`. Reviewed and accepted (August 2026): it reads only files that are already public (`posts.json`, `index.html`, `template.json`), writes nothing anywhere, holds no credentials, and carries `noindex` so it stays out of search results. Keeping it deployed is what lets it be used from any machine without cloning the repo or running a local server.

### Why the bundle includes regenerated pages
A new article page on its own would never be linked from anywhere. The archive and the homepage strip both list every post, so both have to be rebuilt on every publish — which is exactly what `generate_blog.py` does. The publisher reproduces that work in the browser so a post can ship without running Python.

### The two renderers must agree
`publisher/lib/template.js` is a port of `generate_blog.py`'s `card()`, `build_post()`, `build_index()` and `update_homepage()`. Both write the same files, so if they drift, regenerating silently rewrites pages the publisher made. **They currently produce byte-identical output, and changing one means changing the other.** Two things keep it that way:

- `summarise()` is not reimplemented. Every post carries a stored `summary` in posts.json and both renderers just read it — see **Summaries** below.
- `parseBody()` applies the same `[ \t]{2,}` → single-space collapse that `clean()` does, so the stored body matches what Python would write.

To check parity after a change, render the same post both ways and compare.

### The PDF
`publisher/lib/pdf.js` writes the PDF by hand — the page is static, so there is no server and no library to lean on. It uses only the base-14 Helvetica faces, so nothing needs embedding. Layout mirrors `generate_pdfs_v2.py`: Letter, navy headings, 11/17 justified body, blue bullets, contact block, page footers.

A word is a list of styled *segments* rather than a string, because a style can change mid-word: `<strong>…to ask</strong>.` is one word ending in a bold run and a regular full stop. Treating each run as its own word puts a space before the period.

`publisher/lib/zip.js` writes STORED (uncompressed) zip entries. Everything in a bundle is either already compressed or tiny, so DEFLATE would buy nothing.

## Blog

`blog/` holds the archive imported from the live WordPress site. **Do not hand-edit the generated HTML** — change the scripts and regenerate.

| Script | Purpose |
|---|---|
| `extract_blog.py` | Pulls posts + featured images from the flaneyassociates.com REST API into `blog/data/posts.json` and `blog/images/` |
| `generate_blog.py` | Renders `blog/index.html`, one `blog/<slug>.html` per full-text post, and the "latest posts" strip on the homepage |

```bash
python3 extract_blog.py     # refresh content from the live site (needs curl)
python3 generate_blog.py    # rebuild all blog HTML
```

`generate_blog.py` is idempotent — running it repeatedly is safe.

### Locally authored posts
Posts written in `publisher/` live only in `posts.json` and are flagged `local: true`. `extract_blog.py` rewrites that file from the WordPress API, so it deliberately carries local posts across (`local_posts()`); without that, a content refresh would delete them. They also carry `pdf: "articles/<slug>.pdf"`, which is what puts the gated download block on the article page.

### Summaries
Every post carries a stored `summary`. `summarise()` returns it verbatim when present and only derives one from the body as a fallback. This exists because the publisher renders the archive, the homepage strip and the article page in JavaScript: re-deriving a summary from the body in two languages is the one thing guaranteed to drift, and a drifting summary means the card and the `<meta description>` disagree depending on which renderer ran last. For a post written in `publisher/`, `summary` is whatever the author typed in the **Card summary** field.

### Scheduling
Every card and article page carries `data-publish="YYYY-MM-DD"`. `hideScheduledCards()` in `lead-capture.js` hides any card dated ahead of today, and `blog.js` drops those cards from the archive's search, category filters and every count — the hero total, the subtitle, the chip badges and the results line. A scheduled post is committed like any other and simply appears on its own on the right morning; no rebuild, no deploy.

The article page itself stays reachable at its URL so it can be proofed, and `blog.js` puts a "Scheduled preview" banner on it until the date passes.

**Scheduling is presentation, not embargo.** A scheduled post's full text sits in `blog/data/posts.json` and at `blog/<slug>.html` from the moment it is committed, and both are publicly readable — Pages serves a static site, so there is no server that could withhold them. The hiding happens in the visitor's browser. Reviewed and accepted (August 2026): it is what buys the auto-appear behaviour and the ability to proof the real page early, and these are engineering articles rather than embargoed results. **If a post ever genuinely needs an embargo, do not commit it until the day** — no amount of client-side hiding will give you one.

### Gated posts
36 of the 55 source posts sit behind the Simple Membership plugin on flaneyassociates.com; the API returns a login stub instead of a body. Those are flagged `gated: true` and appear on the archive as cards with their real title, date, categories, image and published abstract, badged **Members only** and linking to the source site. **No body text is ever invented for them.** Only the 19 public posts get their own page.

### Content cleaning (`generate_blog.py`)
The source HTML arrives with editor artifacts, handled by `clean()`:
- literal `[vc_*]` / `[wpb_*]` shortcodes are stripped (WordPress renders these server-side, the API does not)
- Gutenberg block delimiters (`<!-- wp:paragraph -->`) are stripped — some posts use blocks rather than WPBakery
- inline `style`/`class`/`id` attributes and wrapper `<div>`s are removed
- `promote_pseudo_headings()` turns bold runs that act as section headings into real `<h3>`s — deliberately conservative, so inline emphasis is left alone
- `drop_leading_title()` removes the title from the top of the body; most posts repeat it, and the page already renders it as the `<h1>`
- `balance_inline_tags()` drops close tags orphaned by heading promotion
- tables are wrapped in `.table-scroll` so wide content scrolls itself, never the page

Titles arrive entity-encoded (`Pglass &#038; PET`), so anything comparing or indexing them must decode first — see `_norm()` and `attr()`.

### Search index
`search_key()` folds curly quotes and dashes to ASCII when writing each card's `data-title`; `blog.js` folds the query the same way. Without this, searching `didn't` misses `didn’t`. Keep the two tables in sync.

### Cache busting
`asset_version()` appends a content hash to `blog.css` / `blog.js` URLs. Without it, returning visitors get new markup with a stale stylesheet or an old search script after a deploy.

`summarise()` builds card and meta descriptions **from the article body**, not the WordPress excerpt: several source excerpts carry shortcodes, repeat the title, or describe a different article entirely. Gated posts have no body, so their published abstract is used once cleaned.

### Homepage integration
`update_homepage()` injects a "Latest from the Flaney Associates blog" strip into the `#blog` section of `index.html`, between the `<!-- BEGIN imported-blog -->` / `<!-- END imported-blog -->` markers. The site's 12 original hand-written blog cards are left in place below it under a "Sector briefings" heading. Regenerating replaces only the marked block.

### Styling
`blog/blog.css` layers on top of `styles.css` and reuses its custom properties. It also defines `.navbar-solid`, because `styles.css` only makes the navbar readable once `.scrolled` is applied — article pages open on a white background and need it from load. `blog/blog.js` handles archive search/filtering plus the nav toggle and scroll state (blog pages do not load the site-wide `script.js`).

## Architecture

### Single-Page Layout (`index.html`)
All content lives in one HTML file. Sections in order: `#navbar → #hero → .trust-bar → #services → #expertise → #process → #industries → #about → #testimonials → #blog → #contact → footer → #downloadModal`.

### Lead Capture System (`lead-capture.js`)
Email validation, the Formsubmit bridge and the gated PDF modal live in `lead-capture.js`, which **every page loads first** — the homepage before `script.js`, blog pages before `blog/blog.js`. It used to sit inside `script.js`, but blog pages never load that file and blog posts now carry their own gated download; one copy beats two that drift. Everything in it is null-guarded, so a page with no modal or no `.gated-download` button is a no-op.

Two lead capture paths both funnel to `sendToFormsubmit()`, which POSTs to `https://formsubmit.co/ajax/info@flaneyassociates.com`:
- **Contact form** (`#contactForm`, wired in `script.js`) — consultation requests, submits name/email/company/service/message.
- **PDF download modal** (`#downloadModal`) — gated downloads; captures name/email/company and the article title before triggering the download. The modal markup is identical on the homepage and on every article page, so `generate_blog.py`'s `download_modal()` and `template.js`'s `downloadModal()` must stay in step.

Captured lead data is persisted in `localStorage` under the key `flaney_lead`. On subsequent visits, returning leads bypass the modal and download PDFs directly.

Email validation (`validateEmail()`) blocks disposable domains (hardcoded list at top of `script.js`) and runs on both forms with 400ms debounce + immediate blur validation.

### Styling (`styles.css`)
CSS custom properties defined in `:root` control the entire colour palette and spacing. Primary brand colours: `--primary: #1a3a5c` (navy), `--accent: #2d8cf0` (blue). Responsive breakpoints at 768px and 480px.

Scroll-triggered fade-in animations are applied via `IntersectionObserver` in `script.js` to all `.service-card`, `.expertise-card`, `.industry-card`, `.testimonial-card`, `.process-step`, and `.blog-card` elements.

### Article Generation Scripts
All three Python scripts share the same brand colour constants (`PRIMARY`, `ACCENT`, etc.) and helper pattern. Each article is a standalone function that receives `story` (reportlab) or `doc` (python-docx) and appends content. A shared `add_contact_footer()` / `footer_block()` is appended to every article.

When adding a new article:
1. Add an article function to the relevant Python script.
2. Register it in the `articles` list in `if __name__ == "__main__"`.
3. Add a corresponding `<article class="blog-card">` block in `index.html` inside the `.blog-grid` div in the `#blog` section, using `data-pdf` and `data-title` attributes on the `.gated-download` button.
